# Plan: multi-platform ad compliance plugin with automatic updates

Written 2026-10-31 for Marcel (GitHub `marcelfelixbaur`). Status: not started.

This plan turns the TikTok skill in this repository into a plugin that will cover every major ad platform over time, gets it to users with automatic updates, and keeps its policy content current with a weekly review. It's written for a fresh Claude Code session that has no memory of the conversation that produced it. Everything that session needs is in this file or linked from it.

The four steps:

1. **Restructure** the repository into a platform-neutral plugin, with TikTok as the first platform.
2. **Add upkeep tooling**: "last reviewed" dates with a staleness warning, a maintenance file, a changelog, and checks that run on every pull request.
3. **List the plugin in Anthropic's plugin directory**, so updates reach users on claude.ai, Cowork and Claude Code automatically.
4. **Schedule a weekly review** that checks for policy and law changes and opens a pull request when something changed.

### Facts this plan relies on (checked 2026-10-31)

Plugins and marketplaces ([create a plugin](https://code.claude.com/docs/en/plugins/create.md), [publish](https://code.claude.com/docs/en/plugins/publish.md), [host a marketplace](https://code.claude.com/docs/en/plugins/host-marketplace.md), [loading and updates](https://code.claude.com/docs/en/plugins/loading.md)):

- **Layout:** a plugin is a folder with `.claude-plugin/plugin.json` (the manifest) and its skills under `skills/<skill-name>/SKILL.md`. Only `plugin.json` goes inside `.claude-plugin/`.
- **Naming:** plugin skills are namespaced, e.g. `/<plugin-name>:<skill-name>`. They still trigger from their description like any skill.
- **Marketplace in the plugin's own repo:** add `.claude-plugin/marketplace.json` next to `plugin.json`, with one entry whose `source` is `"./"` and whose `name` matches `plugin.json`. Users install with `claude plugin marketplace add <owner>/<repo>`, then `claude plugin install <plugin>@<marketplace>`.
- **Auto-update:** off by default for a marketplace like this one. Each user turns it on under `/plugin` → **Marketplaces** → **Enable auto-update**, or runs `claude plugin update <plugin>@<marketplace>`. When on, it runs in the background after a session starts, and new versions load at the next launch or after `/reload-plugins`.
- **Versions:**
  - If `plugin.json` sets `version`, users only get an update when the string changes, so it has to be raised on every release.
  - Set `version` in `plugin.json` only, not in the marketplace entry.
  - The directory warns when `version` is missing, so this plan sets it.
- **Renaming:** never rename a published plugin; existing installs break. Settle the name before the first release.

Anthropic's directory ([submit](https://claude.com/docs/plugins/submit), [pre-submission checklist](https://claude.com/docs/plugins/pre-submission-checklist)):

- **Reach:** one listing reaches claude.ai, Cowork and Claude Code. Claude Code loads it as `<name>@synced` for people who added it on claude.ai.
- **Updates:** people who installed it get each new version automatically once it's published.
- **Who submits and how:** Marcel submits from [claude.ai/directory/manage](https://claude.ai/directory/manage) with a paid plan and his GitHub account connected on claude.ai. The repository must be public when the listing goes live.
- **Repository and folder are permanent:** they can't be changed after submitting. Rename the repository first if it's going to be renamed.
- **How new versions publish:**
  - The directory follows a branch (default `main`) and scans every new commit (validation plus a security scan). A GitHub push webhook makes this immediate.
  - By default an Anthropic reviewer publishes each version. With **Auto-publish passing versions** on, and once Anthropic allows it, later passing versions go live on their own.
- **Checklist highlights:**
  - **Name:** lowercase letters, digits and hyphens. It must be your own distinctive project name. A name that matches a well-known brand (such as "TikTok") in `name`, `displayName` or `author.name` is held for a reviewer. A name made only of generic words is also held.
  - **README** of at least 40 words in the plugin folder, and a `LICENSE` file or `license` field.
  - **Files:** no `.DS_Store`; regular files only (no symlinks or submodules); each non-image file under 256 KiB; at most 512 files.
  - **Security scan:** it checks for undisclosed behaviour. Describe in the README everything the plugin runs, sends or fetches.
  - **Location:** keeping the plugin at the repository root avoids holds that apply to plugins in subfolders.
- **Local check:** `claude plugin validate --profile directory --strict <path>` runs the directory's local checks. It works offline without logging in (tested with Claude Code 2.1.314).

Scheduled tasks ([docs](https://code.claude.com/docs/en/routines.md)):

- **Setup:** created at [claude.ai/code/routines](https://claude.ai/code/routines) or with `/schedule`. A task has a prompt, one or more repositories, a cloud environment, and a schedule (weekly is a preset).
- **What a run does:** each run clones the repository, works on a `claude/`-prefixed branch, and can open pull requests. Commits and pull requests carry Marcel's GitHub user. A run uses the environment's variables, so pick the environment that has the `GIT_AUTHOR_*` variables.
- **Approvals:** a run can't take Marcel's approval as given, so it should never merge on its own.

## 6. Step 4 — Weekly policy review

### Marcel creates the scheduled task (about two minutes)

1. Open [claude.ai/code/routines](https://claude.ai/code/routines) and create a new task.
2. **Name:** "Weekly ad policy review".
3. **Prompt:**

   ```

Commit as Marcel (check git var GIT_AUTHOR_IDENT first). Add no attribution lines to commits or pull request descriptions, and remove any footer the GitHub integration adds to the pull request body.    ```

4. **Schedule:** weekly, at the day and time from D4.
5. **Repository:** `marcelfelixbaur/<repo>`.
6. **Environment:** the cloud environment with the `GIT_AUTHOR_*` and `GIT_COMMITTER_*` variables.
7. **Connectors:** remove all of them. The task doesn't need any.
8. Click **Run now** once to test it.

### Weekly review procedure (copy into `MAINTENANCE.md`)

1. Read `MAINTENANCE.md`: the incorporated change-log entries, the watchlist, and the sources.
2. **Platform policies.** For each supported platform:
   1. Open its current change log. In January, look for the new year's log from the policy index.
   2. List every entry that isn't in the incorporated list, and read each one.
   3. Retry any page in the watchlist that previously failed to load.
3. **Law.** For each watchlist item whose date has passed, or that is marked ongoing, check the primary source for news. Also run one web search per area for changes in the last 14 days: EU advertising and consumer law, AI Act transparency, and the national rules named in `references/law/eu-eea.md`.
4. **Links.** Check that every URL in the reference files' Sources sections still loads. Treat a 403 from a site that blocks bots as "can't check", not as broken.
5. **If nothing changed:**
   - If the newest "Last reviewed" date is older than 28 days, open a small pull request that only updates the dates and raises the patch version. This keeps users' copies from looking stale.
   - Otherwise stop and report "no changes".
6. **If something changed:**
   - Update the affected reference files (including the 2026/2027 change table), and the checker's rules, gates and preconditions where a change affects them. Add a test for each new gate or rule.
   - Update `MAINTENANCE.md` (incorporated list, watchlist) and `CHANGELOG.md`, raise the patch version, and update the "Last reviewed" dates.
   - Run the tests and `claude plugin validate --profile directory --strict .`.
7. **Pull request** titled `Policy update YYYY-MM-DD: <short summary>`. The body has a table of each change (what, which file, source link) and anything it couldn't verify. Remove the footer the integration adds. Don't merge unless D4 says so.
8. **Rules for every run:**
   - Never weaken a check without a primary source.
   - Never remove the "not legal advice" or "approval likely, not certain" wording.
   - Never touch files unrelated to the update.
   - Never assume facts that need the advertiser.

**Done when** the first run's pull request (or its "no changes" report) looks right and its commits show Marcel as the author.

## 7. Adding a platform later

Not part of these four steps. The checklist for when Meta, Google Ads or YouTube is added:

1. Research the platform's ad policies, restricted categories, editorial and character rules, specs and safe zones, and its change log.
2. Add `references/platforms/<platform>/` mirroring TikTok's files. Add the platform to `SKILL.md`'s routing table and its description (still under 1024 characters).
3. Add it to `PLATFORMS` in both scripts. Review every claim rule currently marked `["tiktok"]` and extend the ones that apply. Add the platform's own rules, for example Meta's personal-attributes rule and Google's editorial rules. Add its specs and gates.
4. Add tests for the platform's rules and for leaving TikTok's results unchanged.
5. Add the platform's sources to `MAINTENANCE.md` and the README's platform table. Raise the minor version and add a changelog entry.
